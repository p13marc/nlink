# Upgrading from 0.27.0 to 0.28.0

0.28.0 is a small release with a single theme: **the declarative layer was
describing things it could not actually do, and diffing things the kernel does
not echo.** Both halves of that showed up as a diff that never converged.

One change breaks the build — two enum variants grew fields. Nothing changes
behaviour silently; the two behaviour changes are both "something that always
failed now works".

---

## ⚠️ Compile break

### `DeclaredQdiscType::{FqCodel, Sfq}` gained fields

**Affects:** a `match` that destructures either variant field by field without
`..`.

```rust
// 0.27.0
DeclaredQdiscType::FqCodel { limit, target_us, interval_us } => { … }
DeclaredQdiscType::Sfq { perturb_secs } => { … }

// 0.28.0 — add `..` once
DeclaredQdiscType::FqCodel { limit, target_us, interval_us, .. } => { … }
DeclaredQdiscType::Sfq { perturb_secs, .. } => { … }
```

`FqCodel` gained `flows`, `quantum` and `ecn`; `Sfq` gained `limit` and
`quantum`; `Tbf` gained `peakrate_bps` and `mtu` (it was already
`#[non_exhaustive]`, so that one is not a break). Both new variants are
`#[non_exhaustive]` from now on, as `Netem` and `Tbf` became in 0.27.0, so this
is the last time a knob on them costs a major bump.

**Serde is unaffected.** The new fields are all `Option`, and serde reads a
missing `Option` as `None`, so a document written against 0.27.0 still
deserializes. Serializing now emits the new keys as `null`, which is what netem
has always done.

---

## Behaviour changes

### 1. A declared `masquerade` rule stops diffing as changed

**Affects:** anything reading `NftablesDiff` — `is_empty()`, `change_count()`,
a drift gate built on either.

`Expr::Masquerade` rendered only `NFTA_EXPR_NAME`. The kernel's `nft_expr_dump`
opens an `NFTA_EXPR_DATA` nest for every expression with a `dump` callback and
closes it whatever the callback wrote, so `masq` echoes an **empty** 4-byte
nest that the encoder never produced. The declared body came out 4 bytes short,
and no TLV normalisation can reconcile "one side lacks an attribute" — so the
rule landed in `rules_to_replace` on every diff, forever.

`apply` converged anyway (re-issuing the rule is idempotent and keeps its
handle), so nothing broke visibly. What did break is every consumer that reads
the diff: `is_empty()` was never true for a config containing a masquerade rule.

If you have a drift gate that tolerates "one expected change" on a masquerade
config, **remove the tolerance** — the diff is honest now. A portless
`redirect` had the same omission and is fixed with it.

### 2. `sfq` parameter edits work

`sch_sfq` sets `.change = NULL`, so a same-kind replace — which the kernel
turns into `qdisc_change()` — answered `EINVAL` with *"Change operation not
supported by specified qdisc"*. The declarative applier now falls back to
del+add for that kind when the atomic replace is refused, as it already did for
`ingress`/`clsact`. Changing the *kind* was never affected: that takes the
create-and-graft path.

This was unreachable before 0.28.0 through the builder, because there was no
way to express an sfq parameter at all (see below). It is reachable if you
built a `DeclaredQdiscType::Sfq` by hand or through serde.

## New: the declarative builder can configure fq_codel, sfq, prio and tbf

Not a migration item — nothing you wrote stops working — but the reason the
release exists.

`fq_codel()`, `sfq()` and `prio()` hardcoded every field to `None`, and **no
setter reached any of them**. Through `QdiscBuilder` those three kinds were
"kernel defaults or nothing", even for fields `DeclaredQdiscType` already
carried and the lowering and diff already honoured. Only a hand-written serde
document could reach them.

```rust
NetworkConfig::new()
    .qdisc("eth0", |q| {
        q.fq_codel()
            .limit(1200)
            .target(Duration::from_millis(5))
            .interval(Duration::from_millis(100))
            .flows(1024)
            .quantum(300)
            .ecn(true)
    })
    .qdisc("eth1", |q| q.sfq().perturb(Duration::from_secs(10)).limit(200))
    .qdisc("eth2", |q| q.prio().bands(4))
    .qdisc("eth3", |q| {
        q.tbf(Rate::mbit(100), Bytes::kib(32))
            .peakrate(Rate::mbit(200))
            .mtu(1600)
    });
```

`limit` reaches netem, fq_codel and sfq — all three take a packet count, while
TBF's byte-valued limit keeps `limit_bytes`. `quantum` is shared by fq_codel and
sfq. Every setter is a no-op on a kind that does not have that knob, matching
the netem setters.

### `flows` is create-only, and the diff ignores it

`fq_codel_init` allocates the flow table and `fq_codel_change` opens with

```c
if (tb[TCA_FQ_CODEL_FLOWS]) { if (q->flows) return -EINVAL; }
```

so a change message carrying the attribute is rejected **even when the value is
unchanged**. Left in, it would make every later edit of any other knob fail.

So `flows` is applied when the qdisc is created, dropped from change messages,
and **excluded from `qdisc_params_match`**: a declared-vs-live difference there
is not something a replace could close, and comparing it would put the qdisc in
`qdiscs_to_replace` on every reconcile forever.

The practical consequence: setting `flows` on a qdisc that already exists does
nothing and reports nothing. Delete the qdisc to resize the table.
