# Upgrading from 0.28.0 to 0.29.0

0.29.0 is a netem release. It does three things:

- **It can write the bursty loss models.** Gilbert-Elliott and the 4-state
  model; before this they could only be read back (#368).
- **A netem replace sets the whole state.** Before, it kept whatever it was not
  sent (#370).
- **The docs say what correlation does.** It lowers a loss rate rather than
  making it bursty (#369).

One change breaks the build: `NetemConfig` gained a public field. One method
changes its answer: `NetemOptions::requires_recreation_for`.

---

## ⚠️ Compile break

### `NetemConfig` gained `loss_model`

**Affects:** a `NetemConfig { … }` struct literal that lists every field
without `..Default::default()`.

```rust
// 0.28.0
let cfg = NetemConfig { delay: Some(d), jitter: None, /* …every field… */ limit: 1000 };

// 0.29.0 — build it with the setters (or add `..NetemConfig::new()`)
let cfg = NetemConfig::new().delay(d).build();
```

`cargo semver-checks` finds exactly this one break. `NetemConfig` stays without
`#[non_exhaustive]`; the fluent setters are where new knobs go.

The declarative `DeclaredQdiscType::Netem` variant also gained `loss_model`.
It has been `#[non_exhaustive]` since 0.27.0, so that is not a break. Serde is
unaffected: the field is an `Option`, which a 0.28.0 document simply lacks.

---

## Behaviour changes

### 1. A netem replace now clears what the new config does not set

**Affects:** anything that replaces an existing netem with a `NetemConfig`:
`replace_qdisc`, the declarative `apply`, and `PerPeerImpairer`.

A replace is the kernel's `netem_change()`, which updates only the attributes
it is sent. 0.28.0 sent `rate`, `reorder`, `corrupt` and the correlations only
when set, so a replace that dropped one **kept the old value**. 0.29.0 sends
each one as its off state. A replace now leaves exactly what the config says,
which is what a declaration always meant, and what makes a declaration that
drops `rate` converge instead of being replaced on every `apply()`.

If you relied on a replace *keeping* an old rate or reorder, set it explicitly
in the new config.

### 2. `NetemOptions::requires_recreation_for` answers `true` far less often

It used to say "delete and re-add" whenever the new config dropped a parameter
the live qdisc had. With (1) a replace clears every parameter `NetemConfig`
sets, so it now says `true` only for what `NetemConfig` cannot express and a
replace therefore cannot clear: a live `slot` or ECN.

Code that does

```rust
if current.requires_recreation_for(&new_config) {
    conn.del_qdisc("eth0", TcHandle::ROOT).await?;
    conn.add_qdisc("eth0", new_config).await?;
} else {
    conn.replace_qdisc("eth0", new_config).await?;
}
```

needs no change. It now takes the replace branch where it used to recreate. A
replace keeps the qdisc's statistics and does not drop what it was holding, so
this branch is also the less disruptive one. Example: removing a netem
parameter from a plugged interface no longer loses its backlog.

## Notable additions

### Bursty loss: `NetemConfig::loss_model`

```rust
use nlink::Percent;
use nlink::netlink::tc::{NetemConfig, NetemLossModel};

// tc qdisc replace dev eth0 root netem loss gemodel 1% 30% 50% 0.1%
let model = NetemLossModel::gilbert_elliot(Percent::new(1.0))
    .r(Percent::new(30.0))           // leave the bad state
    .loss_in_bad(Percent::new(50.0)) // tc's `1-h`
    .loss_in_good(Percent::new(0.1)); // tc's `1-k`
conn.replace_qdisc("eth0", NetemConfig::new().loss_model(model)).await?;
```

- **`NetemLossModel::gilbert_intuitive(p13)`** is the 4-state model. Use the
  named `.p31()`, `.p32()`, `.p23()` and `.p14()`: `tc` orders `p23` before
  `p14`, the kernel struct does the opposite.
- **On the declarative path** it is `QdiscBuilder::loss_model`.
- **`NetemConfig::parse_params`** accepts `loss state …` and `loss gemodel …`.
- **A model excludes random `loss` and `loss_correlation`.** Setting both is an
  error at install time; the kernel would silently ignore the random values.

**If you used `loss_correlation` to get bursty loss, it never did.** netem
averages each random draw with the previous one, which lowers a small loss
probability instead of grouping losses: `loss 0.5% 25%` drops 0 of 40 000
packets. Use a loss model.
