# Upgrading from 0.26.0 to 0.27.0

0.27.0 is a **declarative-configuration release**. 0.26.0 was the cycle that
found the places where nothing was checking in the wire layer; this one is
mostly about `NetworkConfig`, `Stack`, and the parts of them that had never
been reconciled twice in a row.

That is the theme, and it is worth stating because it explains the shape of the
list: most of these bugs needed a **second** `apply()` to show themselves. A
declared netem was replaced on every reconcile because the diff compared bytes
the kernel never echoes back. A `Stack` created its WireGuard links after the
addresses that needed them. `ensure_devices` created links and left them down,
so the next layer's routes failed `ENETDOWN`. A purge skipped every table but
main, so a VRF route that left the config never left the kernel. Each is
invisible on a first apply to an empty namespace, which is how a test suite
that only ever applied once kept reporting green.

Two changes break the build, both in the declarative TC builder. Four change
behaviour silently, and **one of them can delete routes a 0.26.0 purge left
alone** — read section 1 before upgrading a reconcile loop that runs with
`with_purge`.

## ⚠️ Silent behaviour changes — read these

### 1. Purge now reaches every table your config declares into

**Affects:** any `apply_with_options` / `apply_reconcile_with_options` with
`purge` enabled, on a `NetworkConfig` that uses `DeclaredRouteBuilder::table`.

0.26.0 added `table` to the route builder, and the add/modify half of the diff
keyed on `(dst, prefix, table)` correctly. The purge half opened with

```text
if r.table_id() != 254 { continue; }     // 254 == main
```

so a declared VRF route that you stopped declaring stayed in the kernel until
the namespace died. Reconcile converged in one direction only.

The purge scope is now **main ∪ every table some declared route names ∪
`DiffOptions::purge_tables`**. Tables your config never mentions — `local`,
`default`, another component's VRF — stay out of reach, which is the fence the
docs always promised.

**What to check before upgrading:** if you declare routes into a VRF table
*and* purge, the first reconcile after this upgrade will remove undeclared
routes in that table — routes 0.26.0 was silently leaving behind. That is the
fix working, but it is a deletion that did not happen last release. Run it once
with `ApplyOptions::dry_run` (honoured by `apply_with_options` and, new this
release, by `apply_reconcile_with_options`) and read the removals before
letting it apply.

Also in this area: a purge whose route vanished between diff and apply no
longer fails the apply. The private `del_route` helper did not swallow `ESRCH`,
so without `continue_on_error` one racing deletion aborted every remaining
removal. It goes through the new `del_route_if_exists` now and counts no
change.

### 2. A declared qdisc is no longer replaced on every reconcile

**Affects:** any `NetworkConfig` with a declared qdisc — netem, tbf, htb,
fq_codel, sfq, prio.

`diff_qdiscs` decided "same kind, different parameters" by rendering the
declared config's `TCA_OPTIONS` and byte-comparing it against the kernel's. The
kernel does not echo what it was sent: netem always reports
`CORR`/`RATE`/`ECN`/`LATENCY64`/`JITTER64`, rounds latency to ticks, and orders
attributes its own way; fq_codel echoes every field with defaults filled in. So
an unchanged declaration compared "different" on **every** `diff()`, and every
`apply()` replaced the qdisc: `changes_made >= 1` forever, statistics reset,
traffic briefly disturbed.

Comparison is now field by field through the parsed `QdiscOptions`, in the
kernel's own units and quantisation. What changes for you:

- a steady-state `apply()` now reports `changes_made == 0`, as everything else
  in `NetworkConfig` already did. **If you keyed anything on the old
  always-nonzero count — a "did something happen" log line, a metric, a retry
  trigger — it will now stay quiet.** That is the point, but it is a
  behavioural difference in code you did not change.
- qdisc statistics survive a reconcile.
- a kind with no parser (anything outside the six above) still falls back to
  the byte compare, so it keeps the old always-replace behaviour.

### 3. `Stack` creates WireGuard links before the network layer, and
`ensure_devices` brings them up

**Affects:** `Stack::apply_in` / `apply`, and any direct
`WireguardConfig::ensure_devices` caller.

Two halves of the same problem. `apply_in` ran `NetworkConfig` first and
`WireguardConfig` last, so a network layer that addressed `wg0` or routed via a
peer's tunnel address failed on a link that did not exist yet. And
`ensure_devices` created links and returned — `add_link` creates a link
administratively **down**, and the kernel refuses a route whose nexthop device
is down (`ENETDOWN`). The documented sequence failed at its second step.

The order is now: declared WireGuard links created **and brought up** →
pre-flight diff → network → nftables → WireGuard keys and peers. A stack with
no WireGuard layer is unaffected.

The silent part is in `ensure_devices`: every declared device is now raised on
**every** call, because that is desired state rather than create-time state.
**A device you deliberately downed by hand comes back up on the next
reconcile.** If you were using "administratively down" as an out-of-band kill
switch on a declared WireGuard link, it no longer survives a reconcile — take
the link out of the config instead.

If you wrote your own `set_link_up` loop to work around this (nlink-lab did),
it is now redundant, and harmless.

### 4. A stale `ip netns` marker is `NamespaceNotFound`, not `EINVAL`

**Affects:** anything matching on the error out of `namespace::{connection_for,
connection_for_async, open, enter}`, the by-name `spawn` / `spawn_with_etc`, or
the sysctl helpers.

`ip netns add` bind-mounts an nsfs inode over an empty file; after a crash or a
bare `umount` the file stays. The by-name paths gated on `Path::exists()`,
which a leftover passes, so the failure surfaced from `setns(2)` as "Invalid
argument" — which nothing downstream recognises as "the namespace is gone".

All eight entry points now resolve through the same `statfs` nsfs check and
return the typed `Error::NamespaceNotFound`, which `is_not_found()` matches,
logging the stale marker at `warn`. **Error-matching code that looked for
`is_invalid_argument()` here needs to look for `is_not_found()`.**

### 5. `NamespaceSpec::Path` now gets the `/etc/netns` overlay

**Affects:** `spawn_with_etc` / `spawn_output_with_etc` with a `Path` spec.

The doc said `Path` and `Pid` "fall back to regular `spawn_path` (no
overlay)", so a caller who switched a node from `Named` to `Path` lost
`/etc/netns/<ns>/hosts` resolution with no error. A `Path` that is an entry of
`NETNS_RUN_DIR` (both `/var/run` and `/run` spellings) now gets the overlay,
because its file name *is* the `ip netns` name the overlay directory is keyed
by. A path elsewhere, and `Pid`, have no name and therefore no overlay — stated
now as a fact rather than a fallback, with `NamespaceSpec::etc_overlay_name()`
to ask which case a spec is in before spawning.

If you relied on `Path` *not* overlaying, that is now `Pid` or a path outside
`NETNS_RUN_DIR`.

Related, and the reason containers stopped working at all here: the sysfs
remount inside `spawn_*_with_etc` was fatal, and inside Docker/Podman it always
failed, so the moment you added a per-namespace `hosts` file every exec in that
namespace broke while plain `spawn` kept working. The replacement sysfs now
copies the read-only/`nosuid`/`nodev`/`noexec` flags of the `/sys` it replaces,
and the rule is stated and followed: **never run with no `/sys`, never refuse
to run over a merely stale one.**

## Compile errors you may hit

These break the build rather than the behaviour, which is the better kind. Both
are in the declarative TC builder.

| change | why |
|---|---|
| `QdiscBuilder::tbf(rate_bps: u64, burst_bytes: u32)` → `tbf(rate: Rate, burst: Bytes)` | The declarative TBF was the last builder taking a bare integer, and the integer meant **bytes** per second. A Rust caller writing `tbf(100_000_000, …)` for "100 Mbit/s" got 800 Mbit/s, with no error anywhere — the exact bug class `Rate` exists to make impossible. Write `tbf(Rate::mbit(100), Bytes::kib(32))`. |
| `match` on `DeclaredQdiscType::Netem { .. }` / `Tbf { .. }` destructured field by field | Both variants gained fields (netem: `rate_bps`, three correlations, `gap`; tbf: nothing new, but see below) and are now `#[non_exhaustive]`. Add `..` to the pattern once; this is the last time a knob on either costs a compile break. |

`DsmarkConfig` and `AtmConfig` are `#[deprecated(since = "0.27.0")]` — a
warning, unless you build with `-D warnings`. See below for why.

The JSON/serde shape of both qdiscs is **unchanged** (`rate_bps` /
`burst_bytes` / `limit_bytes` stay integers in the kernel's units), so a
serialized `NetworkConfig` written by 0.26.0 still deserializes. The new netem
fields are all optional for the same reason.

## Deprecated

- **`DsmarkConfig`, `AtmConfig`** — Linux 6.8 retired `sch_dsmark` and
  `sch_atm` along with CBQ (their companion classifier `cls_tcindex` had
  already gone in 6.3), so on any current kernel an add of either fails
  `ENOENT`/`EOPNOTSUPP` whatever you pass. The types stay for callers on older
  kernels and will be dropped in a later release; `nlink-tc` still dispatches
  `dsmark` and `atm` for the same reason.

  Independently: `DsmarkConfig::new().build()` could never install anywhere.
  Every write in `write_options` was optional, so it sent an empty
  `TCA_OPTIONS` nest, and `dsmark_init` requires `TCA_DSMARK_INDICES` with no
  default — `EINVAL` on every kernel that ever had the qdisc. It now returns a
  `dsmark: indices is required …` error instead of sending a request the kernel
  refuses.

## New

- **`NetworkConfig::apply_reconcile_with_options`** — purge and retry in one
  call. `apply_reconcile` is the retry-on-`EBUSY`/`EAGAIN` shape a
  concurrent-mutator consumer is told to use, but it recomputed the non-purge
  `diff()` every attempt and applied with `ApplyOptions::default()`, so purge
  was unreachable through it. `dry_run` and `continue_on_error` are honoured
  too. Plain `apply_reconcile` is unchanged.
- **`DiffOptions::purge_tables` / `ApplyOptions::with_purge_tables`** — name
  extra route tables a purge may clean, for the caller who owns a VRF table but
  has just stopped declaring into it.
- **`Connection<Route>::del_route_if_exists<R: RouteConfig>`** — the
  table-aware, full-key sibling of `del_route_v4_if_exists` /
  `del_route_v6_if_exists`, which take a bare destination and can only name a
  main-table route. Reports `ESRCH`/`ENOENT` as `Ok(false)`.
- **`Stack::apply_in_with(ns, ApplyOptions)` / `diff_in_with(ns, DiffOptions)`,
  `apply_with` / `diff_with`**, and `facade::apply::{network_in_with,
  wireguard_devices_in}` / `facade::diff::network_in_with` — `network_in`
  called `cfg.apply(&conn)` with no way to pass options, so a `Stack` could
  never purge. Re-implementing the three-call orchestration to get there cost
  nlink-lab about 120 lines.
- **Declarative netem reaches parity with `NetemConfig`** — `rate(Rate)`,
  `delay(Duration)`, `jitter(Duration)`, `jitter_us`,
  `reorder_correlation_pct` (named in the `reorder_pct` doc since 0.21 and
  never implemented), `duplicate_correlation_pct`, `corrupt_correlation_pct`,
  `gap`. `delay_ms` / `jitter_ms` now saturate instead of wrapping above
  4 294 967 ms.
- **`QdiscBuilder::limit_bytes(Bytes)`** — the TBF queue limit, which had no
  builder setter at all.
- **`namespace::list_live()`** — `list()` returns every entry under
  `/var/run/netns`, stale markers included; `list_live()` filters through the
  nsfs check.
- **`impl AsFd for NamespaceFd`, `Connection::new_in_namespace_fd`,
  `NetlinkSocket::new_in_namespace_fd`** — take `impl AsFd` so the borrow
  checker keeps the namespace fd alive for the call. The `RawFd` forms stay.
- **`NamespaceSpec::etc_overlay_name()`** — which spec gets an overlay, before
  you spawn.
- **`NetdevInfo::devtype()`** — `DEVTYPE=`, which net uevents really carry.
- **`QdiscConfig::has_options()`** — default `true`; a config returning `false`
  sends no `TCA_OPTIONS` nest at all. Opt-in rather than a blanket "skip empty
  nests" because the kernel disagrees with itself per kind: `drr` and `qfq`
  classes refuse a missing nest and read defaults from an empty one.

## Corrected documentation

- **`NetdevInfo::driver()` is `None` for every real device.** The
  netdev-lifecycle recipe's table said `driver | ✗ | ✅ (DRIVER=)`, the module
  docs said "uevents know the driver", and five unit tests asserted
  `driver() == Some("veth")` — against uevents they had synthesised
  themselves. The `net` subsystem never emits `DRIVER=`: a net-class device has
  no driver bound, the driver binds to the bus parent, whose uevents are in
  another subsystem and carry no `IFINDEX=` to join on. Measured across veth,
  dummy, bridge, vlan and a virtio NIC. `DriverBound`/`DriverUnbound` have the
  same problem — `KOBJ_BIND` fires on the bus device, so a `subsystem("net")`
  stream never sees one. The accessors stay, documented as reachable only by a
  kernel or driver that does emit the key.
- **`PlugConfig::new().build()` could not install a plug qdisc**, and
  `limit(0)` is not the spelling for the kernel's default — it is a blackhole,
  which the field's doc now says.

## If you use `nlink::lab` for your own tests

`require_root!()` asks `euid == 0`, which is equally true inside a **rootless**
container, where uid 0 is an unprivileged host user wearing a mapping. Most of
what a test does is owned by the user namespace that created it and works
there — but mounting an `/etc` overlay or remounting `/sys` in a spawned
namespace, installing a TC police rate table, and creating a WireGuard device
are checked against `init_user_ns`, and fail `EPERM` no matter which
capabilities the container was granted.

New: `lab::is_host_root()` (the identity mapping in `/proc/self/uid_map`, which
only the initial namespace carries), `require_host_root!()` /
`require_host_root_void!()`, and `NLINK_TEST_STRICT_HOST_ROOT=1` for an
environment that *does* provide host root, which turns the resulting skip into
a failure — the `NLINK_TEST_STRICT_MODULES` bargain, because a silent skip is
indistinguishable from a pass.

If your suite runs in rootless CI and you have tests in those categories,
gate them the same way.
