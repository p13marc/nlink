# Upgrading from 0.32.0 to 0.33.0

0.33.0 starts from a review of 0.32.0 by stream-marker, a daemon that marks
UDP video ports from a declarative nftables table and resets their conntrack
entries (#889). Its first changes fix what that review found:
- a conntrack delete that flushed the whole table;
- reconcile futures that could not be spawned;
- per-family conntrack flushes that flushed both families;
- route constructors that turned a typo into a default route.

Read the behaviour changes as well as the compile breaks: one of them changes
what an existing call does, with no compile error.

## Compile breaks

### `del_conntrack_by_id` is gone; delete the entry the dump returned (#878)

`del_conntrack_by_id(id)` sent the id alone. The kernel finds a conntrack
entry by its tuple and checks the id only after that, so it took the
request for a flush of the whole table: every entry in the namespace, both
families, every zone. Nothing can delete by id alone, so the method is
removed rather than fixed. Delete the entry itself:

```rust
// 0.32
let id = entry.id.unwrap();
nf.del_conntrack_by_id(id).await?;

// 0.33: sends the entry's family, original tuple, zone and id
nf.del_conntrack_entry(&entry).await?;
```

The kernel still checks the id. If the flow was replaced by another one
with the same tuple since the dump, the call fails with `is_not_found()`
and the new flow stays.

### `ConntrackEntry` has `family` and `zone`, and is `#[non_exhaustive]` (#883)

Dumps and events fill both. `zone` is `None` for the default zone, which
the kernel does not report. A struct literal outside nlink no longer
compiles; entries come from the kernel, and a test that needs one by hand
starts from `ConntrackEntry::default()` and sets fields:

```rust
let mut entry = ConntrackEntry::default();
entry.proto = IpProtocol::Udp;
entry.orig = ConntrackTuple::v4(src, dst).ports(40000, 5000);
```

`ConntrackBuilder::from_entry(&entry)` starts a builder from an entry, and
`ConntrackBuilder::family()` returns an `AddressFamily` instead of a raw
`u8`: compare it with `AddressFamily::Inet` / `Inet6`, or use
`u8::from(..)`.

### Route destinations are `Ipv4Addr` / `Ipv6Addr` (#881)

`Ipv4Route::new`, `Ipv6Route::new`, `del_route_v4`, `del_route_v6` and the
two `_if_exists` deletes took the destination as a string, and turned one
that failed to parse into `0.0.0.0` or `::` with no error. With prefix 0,
that was the default route, added or deleted. They take an address now:

```rust
// 0.32
Ipv4Route::new("10.0.0.0", 8)
conn.del_route_v6("2001:db8::", 32).await?;

// 0.33
Ipv4Route::new(Ipv4Addr::new(10, 0, 0, 0), 8)
conn.del_route_v6(Ipv6Addr::new(0x2001, 0xdb8, 0, 0, 0, 0, 0, 0), 32).await?;
```

A destination from user input parses first, and the caller sees the error:
`Ipv4Route::new(input.parse()?, prefix)`. `Ipv4Route::default_route()` and
`Ipv6Route::default_route()` are unchanged.

### `NftablesDiff`'s rule deletes and replaces are structs (#708)

`rules_to_delete` was a `Vec<(table, family, chain, handle)>` and
`rules_to_replace` a `Vec<(table, family, chain, handle, rule)>`. They are
`Vec<RuleDelete>` and `Vec<RuleReplace>` now, with the same fields by name,
and each adds `current`: the rule the kernel has, as `nft -s list` prints
it, or `None` where nlink cannot print it. A delete also has the rule's
`key`. `RuleMove` gains the same `current`.

```rust
// 0.32
for (table, family, chain, handle) in &diff.rules_to_delete { /* … */ }
for (table, family, chain, handle, rule) in &diff.rules_to_replace { /* … */ }

// 0.33
for d in &diff.rules_to_delete {
    tracing::info!(table = %d.table, chain = %d.chain, handle = d.handle.0,
                   rule = ?d.current, "deleting");
}
for r in &diff.rules_to_replace {
    let (from, to) = (r.current.as_deref(), r.rule.body().nft_syntax_stateless());
}
```

Both are `#[non_exhaustive]`; the diff makes them. In the diff's JSON, the
two arrays' items are objects (`table`, `family`, `chain`, `handle`, and
`key` and `current`), not arrays.

### A declared chain's JSON holds its `kind` (#708)

In a diff's JSON, a `DeclaredChain` (in `chains-to-add`, `chains-to-modify`,
`chains-to-recreate`) had flat `hook`, `priority`, `policy`, `chain-type`
and `devices` fields. It has `kind` now: `"regular"`, or `{"base": {"type",
"hook", "devices", "priority", "policy"}}`, with `devices` and `policy`
left out when empty.

### `DeclaredRule::exprs()` returns what the rule sends (#708)

A rule's body is a `RuleSpec` now, and the builder's methods append items
to it rather than expressions. `exprs()` returns `Result<Vec<Expr>>`: the
spec lowered for the table's family, or why it does not lower, the error
`validate()` reports. That is the list the kernel is sent, with
the guards nft writes: each once, none that the family implies, and `meta
protocol` in a bridge or netdev table. Code that matched on the builder's
own list, an `nfproto` guard in an ip table for instance, sees the list the
kernel has. `spec()` returns the body.

```rust
// 0.32
let last = t.rules()[0].exprs().last().cloned();

// 0.33: an owned Vec, or the rule's error
let last = t.rules()[0].exprs()?.last().cloned();
let items = t.rules()[0].spec().items();
```

### `tables_refused`, `kept_in_use` and `blocked_by` are `blocked` (#708)

What the diff cannot do, or leaves alone, is one list, `NftablesDiff::blocked`:

| 0.32 | 0.33 |
|---|---|
| `diff.tables_refused` | `Blocked::TableFlags { family, table, from, to }` |
| `ChainRecreate::blocked_by`, `is_refused()` | `Blocked::ChainRecreate { chain, reason, rules, .. }`; a refused chain is not in `chains_to_recreate` |
| `diff.kept_in_use: Vec<KeptInUse>` | `Blocked::InUse { item: NftItem, rules }` |

```rust
// 0.32
if !diff.tables_refused.is_empty() { /* … */ }
// 0.33
if diff.blocked.iter().any(Blocked::refuses) { /* apply will fail, and why */ }
for blocked in &diff.blocked {
    tracing::warn!(%blocked, "nftables");
}
```

In JSON, `tables-refused` and `kept-in-use` are gone; `blocked` holds
`{"kind": "table-flags" | "table-recreate" | "chain-recreate" | "bound" |
"in-use" | "unmodelled-object", …}`. An item is `{"type": "set", "table",
"family", "name"}`.

## New: the diff as typed changes (#708)

`NftablesDiff::changes` says what a diff changes as `Change<T>` values,
with what the kernel holds and what it will hold:

```rust
for change in diff.changes.iter().flat_map(NftChange::flatten) {
    if let NftChange::Rule(Change::Update { from, to }) = change {
        tracing::info!(rule = ?to.key, from = ?from.nft, to = ?to.nft, "rule changes");
    }
}
for set in diff.sets() {
    if let Change::Recreate { reason, cascade, .. } = set {
        tracing::warn!(%reason, moved = cascade.len(), "set recreated");
    }
}
```

The per-kind lists (`rules_to_add`, `sets_to_delete`, …) are what
`apply` sends; read the changes instead.

## New: rules as data (#708)

A `RuleSpec` is a rule's body as values. It has items in order, each a
`Match { field, op, value }`, a `Stmt`, a `Verdict` or a raw `Expr`, and
a comment. `push_rule` declares a spec with no closure, and `try_rule`
takes a closure that can fail:

```rust
use nlink::netlink::nftables::{Field, Match, RuleSpec, Stmt, Value, Verdict};

// 0.32: a port range with != was built by hand, from Payload and Cmp
// expressions with a v4/v6 dispatch; a parse error had to .expect().
// 0.33
let drop_high = RuleSpec::new()
    .then(Match::ne(Field::TcpDport, Value::range(1000u16, 2000u16)))
    .then(Match::ne(Field::Iifname, "lo"))
    .then(Stmt::Counter)
    .then(Verdict::Drop);
let cfg = NftablesConfig::new().table("t", Family::Inet, |t| {
    t.chain("input", |c| c.base(BaseChain::filter(FilterHook::Input, Priority::Filter)))
        .push_rule_keyed("input", "drop-high", drop_high)
        .try_rule_keyed("input", "trusted", |r| {
            let src = src.parse().map_err(|_| nlink::Error::invalid_message(format!("{src}: no address")))?;
            Ok(r.match_saddr(src, 8).accept())
        })
});
```

A kernel rule reads back the same way: `RuleInfo::spec()` lifts its
expressions to items, which lower to the rule again. Anything nlink has no
item for stays a raw `Expr`.

```rust
for rule in conn.list_rules("filter", Family::Inet).await? {
    let spec = rule.spec();
    let ssh = spec.items().contains(&Match::eq(Field::TcpDport, 22u16).into());
}
```

A `Rule` method and the item it appends lower to the same expressions, so
existing rules send what they sent. On a flag set (`ct state`, `ct status`,
`ct label`, `tcp flags`), `Match::eq` is nft's `ct state
established,related`, any of the flags. `Match::ne` is nft's `ct state !=
established`: the field is not exactly the value. Write "none of" as
`Value::Masked { value: 0, mask }`.

## Deprecated

### The chain setters: build a `BaseChain` (#708)

`hook`, `priority`, `chain_type`, `policy` and `device` on `Chain` and on
`DeclaredChainBuilder` still work, and warn. A `BaseChain` describes the
same chain, and cannot describe one the kernel refuses:

| 0.32 | 0.33 |
|---|---|
| `.hook(Hook::Input).priority(p).chain_type(ChainType::Filter)` | `.base(BaseChain::filter(FilterHook::Input, p))` |
| `.hook(Hook::Postrouting).priority(p).chain_type(ChainType::Nat)` | `.base(BaseChain::nat(NatHook::Postrouting, p))` |
| `.hook(Hook::Output).priority(p).chain_type(ChainType::Route)` | `.base(BaseChain::route(p))` |
| `.hook(Hook::NetdevIngress).device("eth0")` | `.base(BaseChain::filter(FilterHook::ingress("eth0"), p))` |
| `.hook(Hook::InetIngress).device("a").device("b")` | `.base(BaseChain::filter(FilterHook::ingress(["a", "b"]), p))` |
| `.hook(Hook::NetdevEgress).device("eth0")` | `.base(BaseChain::filter(FilterHook::egress("eth0"), p))` |
| `... .policy(Policy::Drop)` | `BaseChain::filter(..).policy(Policy::Drop)` |

A chain without `.base(..)` is a regular one. Where the parts come from a
file or a command line, `BaseChain::try_new(chain_type, hook, priority,
devices)` returns the error the old setters left to `validate()`.
`Hook::NetdevIngress`, `Hook::InetIngress` and `Hook::NetdevEgress` are
deprecated for `Hook::Ingress` and `Hook::Egress`, which
`Hook::number(family)` numbers by the table's family.

## Behaviour changes

- **A recreate a hand-added rule depends on is refused (#708).** A set,
  object or flowtable the diff recreates, used by a rule nlink did not
  write, used to fail at commit with `EBUSY`. `apply` now refuses it first,
  with `NotSupported` naming it, and nothing changes. An owned table
  recreated for a new comment, holding such rules, is refused too. It used
  to delete them.
- **The diff compares every base chain's type and priority (#708).** A
  chain declared with a hook and no type or priority is a filter chain at
  priority 0, as the kernel creates it. A declaration that left them out
  used to accept any type and priority on the kernel's chain. Now a chain
  of another type or priority is recreated. `DeclaredChain::chain_type()`
  and `priority()` return `Some` for every base chain.
- **`Connection::add_chain` and `Transaction` check a chain before sending
  it (#708).** They refuse what `validate()` refuses: a hook the family
  does not have, a nat or route chain outside ip, ip6 and inet, a policy
  without a hook. Before, the kernel refused these. A chain with a hook
  and no type is a filter chain, where `add_chain` used to refuse it.
- **An ingress chain in an ip or ip6 table fails `validate()` (#708).** The
  kernel refused it at apply time (`EOPNOTSUPP`). Only inet's has one.
- **`Priority` compares by value (#708).** `Priority::Custom(0) ==
  Priority::Filter`.

- **The diff prints rules as `nft -s list` does (#708).** A declared rule's
  text in `NftablesDiff`'s `Display` and JSON is stateless: `counter`, not
  `counter packets 0 bytes 0`, and a quota without what it has used. The
  kernel's side prints the same way, so a rule reads the same whatever
  traffic it has counted. `nft_syntax()` keeps the counts.

- **`flush_conntrack()` leaves IPv6 entries; `flush_conntrack_v6()` leaves
  IPv4 ones (#880).** Both were documented as per-family and flushed both
  families. A program that called `flush_conntrack()` to empty the whole
  table calls `flush_conntrack_all()` now. One that called both flushes
  can keep doing so, or call `flush_conntrack_all()` once.
- **`del_conntrack` refuses a builder with no tuple (#878).** The kernel
  took a delete without one for a flush of the whole table, so
  `del_conntrack(ConntrackBuilder::new_v4(..))` emptied it. It is now an
  `ErrorKind::Invalid` error, and nothing is sent.
